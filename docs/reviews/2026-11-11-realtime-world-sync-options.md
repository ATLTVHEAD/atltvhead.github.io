# Realtime shared-world synchronization options

Research date: 2026-11-11. **Decision NET-01: OPEN.** This is a decision briefing, not an approved architecture, provider selection, implementation plan, or authorization to build a backend.

## The short answer

**PROPOSED direction for investigation:** keep skating responsive locally; explore asynchronous, bidirectional server push with periodic movement snapshots plus event-driven shared actions, rather than pulling the whole world every render frame. The rate should be expressed in updates per second, independent of rendering, and measured rather than assumed. This timing recommendation does **not** select who is authoritative over movement, which server or provider to use, or what happens on overload.

The two halves of the question are not mutually exclusive: a connection can receive messages asynchronously while movement snapshots are sent periodically. Polling is possible, but repeatedly asking for unchanged state adds requests and delays detection until the next poll. Push still needs pacing, recovery, and resource limits; it is not magically instantaneous or loss-proof.

## Problem, boundaries, and repository evidence

The user wants one public **shared world** on the website, not private lobbies or shards. Initial validation is **12–16 simultaneous participants**, not a maximum or promised capacity. Eventually **playtest bots** should roam and trick; player collisions, ragdolls, and head-to-head play are later. Three.js, desktop/gamepad first, then phone, remain requirements. There are no accounts, saved profiles/progress, chat, or product analytics in scope. Gameplay state is ephemeral. A stopped player places a curated tag on a suitable reachable wall; tags may overlap and fade over two minutes; no gameplay cooldown; each session can have five active tags, and a sixth removes its oldest.

Source observations, not assumptions about a live deployment:

- `js/game/core/fixed-step.js:41–60,89–120` defaults to 60 simulation steps/second, bounds catch-up and consumes input edges; `js/game/runtime/game-session.js:101–127,146–173` advances it on animation frames and only joins local play. `js/game/main.js:330–360` renders the current local state. This is a useful existing distinction, not a network implementation.
- `js/game/core/local-play.js:99–144` composes one skater's motion/tricks; `js/game/world/tag-targets.js:244–287` contains a reach/anchor query, not an implemented shared tag lifecycle. `js/game/shared/world-config.js:11–14` says 12 guests and 5 Hz, but the foundation audit found these constants unused. Neither is an approved cap or measured rate.
- `package.json:10–16` describes static deployment and references a missing room configuration; the foundation audit §5 reports no transport, server, remote avatars or multiplayer tests. The old Cloudflare room plan was historical, not a current decision. The audit also identifies movement/contact defects: replicating the existing simulation does not validate it.
- GitHub describes Pages as static hosting [S1]. A shared world needs a separately supplied service or coordination, even if the webpage stays on Pages. No existing ADR was found in `docs/adr/`; no existing architectural decision is silently reopened here.

## Three clocks and what travels

1. **Simulation clock:** advance physical/gameplay logic by a fixed duration where appropriate, currently 1/60 second locally. A server simulation could have its own step; its exact cadence is OPEN. A fixed timestep alone does not guarantee cross-runtime determinism.
2. **Network clock:** publish or batch snapshots on a wall-clock cadence measured in Hz, independent of the display. Async actions can be sent when they occur. Timers may drift or be throttled, especially in background tabs; timestamps, bounded catch-up and stale-state handling matter.
3. **Render clock:** animate on the browser's available frames, which can differ across devices and vary. “Every three frames” is not a stable network rate across 30/60/120 Hz displays.

**Illustrative experiment, not a requirement:** compare 10–20 movement updates/second and appropriate interpolation buffers with a lower/higher control; test actual skating and networks. Colyseus v0.18 documents a default 50 ms state patch (20 Hz), and Cloudflare discusses 50–100 ms batching as general high-frequency guidance [S4, S6]. Neither source proves these settings work here; batching also adds waiting time. Existing unused 5 Hz is another experimental comparator, not evidence of suitability.

Local response can be immediate instead of waiting for a round trip. Under server-authoritative movement, the client **predicts** its own input and, on an acknowledged authoritative state, reconciles and replays unacknowledged inputs; visible corrections need care. Under client-authoritative movement, local motion is immediate without the same server reconciliation contract, but claims are more easily forged. For others, buffer timestamped snapshots and **interpolate** behind real time; extra buffering smooths jitter but adds visual delay. If snapshots stop, bound any extrapolation and mark/freeze/remove stale avatars rather than invent indefinitely. Handle world-wrap seams, respawns and large corrections explicitly so interpolation does not travel the long way across the district. Colyseus's netcode guidance distinguishes fixed simulation and prediction [S5]; these are patterns, not an assertion this game is deterministic.

## Alternatives — none selected

| Option | Benefits | Costs, failure modes and reversibility |
| --- | --- | --- |
| **A. Server-authoritative inputs and simulation** | Shared source of movement truth; stronger basis for future interactions and rejecting impossible motion. Server can decide whether tagging is valid. | More server CPU and implementation complexity, ongoing simulation and world-version consistency; input latency requires prediction/reconciliation for feel. Prediction can diverge, especially with later physics/collisions. Changing later requires protocol and simulation migration, not just a setting. |
| **B. Client-authoritative local movement; shared service authorizes presence and tags** | Preserves responsive local skating, less server simulation, relatively simple presence snapshots. Shared tag cap/order can be enforced centrally. | A modified client can claim movement or fake being stopped/within reach. Plausibility checks catch some teleports or malformed data, not all cheating; strict checks may reject legitimate movement, lag or wrap seams. Later competitive interactions likely require reopening authority. Migration to A changes contracts and validation. |
| **C. Peer-to-peer WebRTC plus signaling, with a peer or service coordinating shared state** | Potential direct paths and reduced central movement relay in some networks; configurable data-channel behavior. | Still needs signaling and often STUN/TURN; peer churn, NAT and relay costs; a player-host can disappear or cheat. A full mesh grows as N(N−1)/2 connections, and coordination of the five-tag rule and late joins is nontrivial. Replacing it later changes topology/protocol. MDN documents signaling and relay candidates [S3]. |
| **D. Keep existing local-only game** | No new network dependency or operational spend; easiest to reverse by building later. | Does not meet the shared-world goal or synchronize tags; useful only as an explicit baseline, not a solution. |

**Reasoned recommendation:** investigate a centrally coordinated, asynchronous push prototype and compare A versus B on skating feel, operating costs, and acceptable manipulation; B may be simpler for noncompetitive presence, while A is a stronger future-interaction foundation. These are hypotheses, not an authority choice. A conventional hosted Node.js service (possibly using Colyseus) and a managed stateful service such as Cloudflare Durable Objects are deployment examples, not endorsements. A conventional host needs process lifecycle, deployment, monitoring, recovery and scaling operations; managed services add vendor-specific lifecycle/limits and potentially lock-in. Colyseus rooms are isolated groups [S4]; choosing the framework does not mean accepting multiple gameplay worlds.

## Concrete message-flow illustration — PROPOSED, conditional on a shared authority

This is an example to expose requirements, not a wire protocol or selected trust model.

1. A visitor joins over an encrypted connection. A service assigns a temporary session identifier, verifies compatible world/protocol versions and sends a consistent baseline: current participants, poses and active tags with a world epoch, ordering/version cursor, and authority time/expiry information. IDs are ephemeral, not accounts. A reconnect token, grace window and whether reconnect retains session identity are **OPEN**.
2. The skater moves immediately. Depending on A or B, the client sends sequenced input commands or bounded pose claims at a separately paced cadence. The service publishes dated snapshots; receivers interpolate. In A, snapshot acknowledgments support replay; in B, any server correction is only as trustworthy as its validation. Hidden/suspended tabs, disconnects and stale avatars need explicit policy.
3. On Tag, send an action identifier, curated design/color and wall anchor. The authority checks payload size/schema, finite numeric values, allowed design and world version, valid surface/reach, and stopped status against the state it actually trusts. Under B those last checks can only use client claims plus plausibility checks; they do **not** prove honest location. An authoritative simulation can check its own state but still needs a policy for network timing. Check movement bounds, plausible speed/displacement and wrap-aware distance to catch obvious teleports; normal lag, game mechanics and packet timing make thresholds nontrivial.
4. If accepted, the authority applies the five-per-session rule atomically: on a sixth active tag remove the oldest, then add the new tag, using a deterministic tie-breaker for simultaneous arrivals. Return acceptance/rejection to the requester and publish ordered add/remove changes. Overlap is allowed. A retry of the same action ID must not create another tag. No cooldown is implied.
5. The authority supplies a creation/expiry time so everyone computes the same two-minute fade, and expires/removes tags independently of whether an originating player remains connected. Exact fade curve and whether tags survive an intentional leave, session expiry, or server restart until their two minutes end are **OPEN**. Snapshot/resync must exclude expired tags even if cleanup was delayed. Decide and document how a late join or reconnect obtains remaining lifetime without trusting the client's wall clock; clock-offset estimation has uncertainty.
6. Baseline plus subsequent changes need an atomic cursor/cutover or buffered replay: a placement concurrent with a join must not be missed, duplicated, resurrected after removal, or reordered. Apply versions/epochs, deduplicate retries, and request a fresh baseline on gaps, reconnect or epoch change. Define what an accepted-but-unacknowledged action means across disconnect/restart; transport delivery is not proof the application applied it. Reset ephemeral state on restart unless a separately approved recovery design says otherwise.

WebSocket is a long-lived bidirectional connection over TCP [S2, S6]. Its ordered reliable stream retransmits lost network data while a connection remains viable; it does **not** mean packets cannot be lost, eliminate latency, or guarantee an application action was committed across disconnects. Loss can delay later messages behind earlier bytes. Pose data becomes stale: coalesce unsent poses before enqueueing where feasible, never build unbounded queues, and disconnect/resync slow clients under an approved policy. Already queued TCP bytes cannot simply be replaced. MDN notes the browser WebSocket API has no automatic backpressure and exposes queued `bufferedAmount` [S2]. Important tag events require idempotency and resync, not a claim of guaranteed exactly-once delivery.

## One public world, capacity and safety

A single *logical* world means participants share the same public state and can encounter one another. It does not require a single physical process forever: internal spatial filtering or coordinated components could reduce work without creating invisible separate copies. Such scaling changes require separate design approval. A central process is simpler initially but has finite CPU, memory, bandwidth, geographic latency and failure limits. All-to-all full-pose broadcast scales approximately with N(N−1) delivered player updates per interval; batching reduces envelope overhead, not the amount of recipient state in the worst case. Rendering N avatars also costs the client. Twelve to sixteen is a validation scenario, not a capacity guarantee or automatic cap.

The five-tag rule bounds active tags **per session**, not session creation, rapid replace events, egress, parsing, event logs, or total world memory. A public anonymous endpoint can be spammed by many connections. **OPEN security/overload decisions:** message and payload bounds, validation, origin/upgrade controls, connection/admission budgets, slow-consumer handling, resource budgets, global memory caps and fair abuse mitigations. Rate limiting or rejecting abusive traffic could conflict with the intended no-cooldown experience, so any safety limit and its player-visible behavior need explicit approval. If capacity is exhausted, options include bounded queue/retry, temporary admission refusal, or reducing update detail; none is selected. Do not silently create another world or promise unlimited players.

Ephemeral game state does not mean no metadata: network providers necessarily see connection information; GitHub says Pages logs visitor IP addresses for security [S1]. Cloudflare's optional WebSocket analytics dataset includes client IP and connection fields [S9]; that is not evidence this project enables it. Avoid claiming anonymity or zero logs. Retention, access, disclosure, privacy policy, diagnostic aggregation and provider defaults are OPEN, consistent with no product analytics. Temporary IDs should not be treated as accounts or persistent profiles.

## Provider facts, not a deployment decision

As documented on 2026-11-11, Cloudflare's Durable Object WebSocket hibernation can keep sockets connected while the object leaves memory, but its in-memory state resets; regular timers prevent hibernation [S6]. Thus tags and session state cannot simply be assumed to survive hibernation; restoring them, opting out of hibernation, or resetting them are different lifecycle/persistence decisions. Continuous updates can reduce hibernation benefit. Cloudflare documents a single object as single-threaded with a soft 1,000 requests/second whose actual throughput varies with workload, and overload errors [S7] — not a player-capacity benchmark. Its pricing documentation lists free daily quotas and paid request/duration/storage charges; incoming WebSocket messages have a billing-only 20:1 ratio, and exceeding a free limit can fail operations [S8]. These costs are workload-dependent, not a cost estimate. Recheck terms and limits before any choice.

Colyseus v0.18 exposes a server loop, patches, validation and reconnection support [S4, S5]; it is a framework requiring a hosting/operations decision and potential dependency/license review. Neither vendor's examples validate this game, its capacity, security or latency. Valve's community networking page appeared in search but was blocked by an anti-bot challenge on direct access, so it is **not** used as verified evidence here.

## Verification that would reduce uncertainty — PROPOSED

- Compare A and B with identical representative skating inputs and real human play, including jumps, grinds, wall-ride ambitions, wrap boundaries, stoppage and simultaneous tagging; measure local input-to-display responsiveness, remote visual error, correction frequency/magnitude and perceived smoothness across latency, jitter and loss profiles. Record interpolation delay and update cadence separately.
- Use 12–16 concurrent participants as the first target, then increase load until clear degradation; measure server CPU/memory, bytes and messages per direction, tick/update delays, connection success, client rendering FPS/memory and expected provider cost. Establish user-approved budgets before treating any result as pass/fail; test desktop/gamepad first and phone later.
- Include **faithful playtest bots** that use real protocol, move around the district and execute tricks, not only idle connections. Synthetic traffic and bursts remain useful for isolated saturation but do not prove gameplay feel or realistic rendering. Test 5 Hz and the illustrative 10–20 Hz range, plus higher rates if warranted.
- Exercise rapid no-cooldown tag replacement, concurrent sixth placements, overlapping tags, expiry while nobody is nearby, late join during mutation, duplicate IDs, dropped acknowledgments, stale/out-of-order versions, reconnect, restart, clock skew, slow consumers, malformed messages, oversized payloads, forged positions, false stopped claims, session churn and resource exhaustion. Verify recovery and consistent visible state, not merely that messages were sent.
- Before later physical player collisions or head-to-head play, explicitly test simulation reproducibility across runtimes, input replay, nondeterministic ordering and latency fairness; fixed timestep alone is insufficient. Revisit collision ownership and trust rather than assuming either A or B automatically solves them.

**NET-01 OPEN:** authority/trust boundary, transport, cadence, hosting and recovery remain undecided. Also open: acceptable cheating versus cost/feel, global reachability/latency, session retention after disconnect, two-minute fade curve and tag survival on leave/restart, version compatibility, admission/abuse budgets, privacy retention, and measurable acceptance thresholds.
