# Browser game engine options

Research date: **2026-11-11**. **ENGINE-01 — APPROVED direction:** after this research began, the user reaffirmed Three.js for rendering with focused libraries. Rapier collision services remain the approved direction for evaluation; package/version and integration are open. No implementation milestone is approved by this report. The alternative-engine comparison below is retained as reference, not an open migration decision.

## Short answer

Yes. **Babylon.js and PlayCanvas are browser-oriented JavaScript/TypeScript 3D engines**, rather than desktop engines merely exported to the web [B1, P1]. Three.js is also browser-native; pairing it with Rapier's WebAssembly physics does not make the application a desktop-engine port [T1, R1]. WebAssembly is a browser execution format, not a sign that an engine is unsuitable for the web. Godot and Unity also export browser clients; Unreal's documented Pixel Streaming is a different model in which a remote machine renders video [G1, U1, E1].

**APPROVED direction:** retain Three.js for rendering with focused libraries; pursue Rapier collision services for evaluation. Babylon.js, PlayCanvas and Godot are useful comparisons if the user later reopens that choice, not required experiments. Unity is a credible web-export alternative, not automatically excluded by mobile support; its commercial terms and C# workflow need review. Unreal local browser export on current UE5 is **unverified**, not declared unsupported here. No new dependency or implementation milestone is authorized by this report.

## Retained goals and repository evidence

The parent-relayed decisions documented in `2026-11-11-skating-controller-options.md` §1 and `2026-11-11-realtime-world-sync-options.md` include a bounded, original multilevel **District**, momentum-based aggressive inline skating, natural takeoffs, deliberate Grind and Wall ride, Boost, comic-style presentation, one public **shared world**, and initial shared presence and **Tagging**. Tags are temporary, curated and subject to the five-active-per-visitor rule. Twelve to sixteen simultaneous visitors is an initial validation workload, **not a hard cap**; future Playtest bots can explore limits. Desktop/gamepad is first and phone touch second. A 30 fps target needs validation, not an assertion that any option achieves it. Player impacts, ragdolls and challenges are later. The preferred Blender MCP candidate is subject to separate trust/setup approval. These goals do **not** dictate an engine, server provider or algorithm. The prior Three.js choice is not silently superseded; explicitly reconcile it before a change.

**Observed in this checkout:** `skate.html:113–118` loads vendored Three r137 and GLTFLoader before `js/game/main.js`. `index.html:64–73` independently uses the same Three library for the non-game viewer. The game entry creates both preview and play scenes, initializes a Three WebGL renderer, owns input/session/lifecycle and calls `joinLocal` (`js/game/main.js:84–163,291–361,379–425`). The local asset loader fetches a manifest, checks hashes and uses Three's GLTFLoader (`js/game/render/game-assets.js:21–90`). `package.json:7–16,31–33` declares Three `^0.137.0` and an echo-only static build. The foundation audit records existing contact defects and no functional multiplayer; a renderer switch does not inherently correct either (`2026-11-11-skate-game-foundation-audit.md` §§1–2,5). The world-authoring report explains that the current importer and renderer do not extract general authored collision/rail semantics (`2026-11-11-world-authoring-options.md` §§2,4). No ADR directory was found.

**Migration inference:** replacing the game renderer affects scene construction, assets/materials, camera, lifecycle, tests, and embedding; it need not replace the portfolio viewer or all pure JS game rules. Running both engines on separate pages may preserve the site but creates two runtime/dependency maintenance surfaces. A newer Three release also has migration cost; r137 is not evidence of current Three capabilities. No cost estimate or migration has been measured.

## Clarifications that matter

### PlayCanvas: engine, hosted editor, project privacy and self-hosting

The [engine repository](https://github.com/playcanvas/engine) is MIT, documents standalone local development and glTF, and lists ammo.js integration [P1, P2]. The [Editor frontend repository](https://github.com/playcanvas/editor) is also MIT and documents a local frontend development build that still opens a project at playcanvas.com. That is **not proof of a complete offline, self-hosted Editor backend** [P5]. A locally developed engine app does not require the hosted Editor; an exported app can be downloaded for self-hosting under the listed plans [P1, P3]. Self-hosting the **published app** is not equivalent to preserving an independently editable Editor project; inspect project backup/import capabilities and third-party asset terms before relying on it.

As listed on the mutable plan page on the access date, the free Editor plan is $0, provides 1 GB storage and unlimited public projects; Personal is $15/month with private projects and 10 GB, Organization $50/seat/month with 50 GB. Cancellation locks private projects until resubscribing or making them public [P3]. Official docs say a fork of an eligible public project copies scenes, assets including models/textures/scripts and settings; exceptions include owners who keep source assets private and other non-forkable cases [P4]. Thus **do not assume free public Editor project assets are confidential**; check the actual source-asset privacy setting and terms. Publicly delivered game files can also be retrieved by a browser; public access does not itself establish a license to reuse artwork. Verify retention, terms, privacy and current prices before uploading any nonpublic work. No account or upload occurred.

### Physics, assets and AI are independent choices

Babylon's official Havok example explicitly initializes the WASM library and passes it into `HavokPlugin`; PlayCanvas documents ammo.js-based rigidbody and collision components and alternatives [B2, P2]. Rapier has an independent JS binding and controller [R1]. A scene graph, collider or third-party demo is not a tested aggressive-inline-skating motor. In particular, deliberate rail paths, wall eligibility, contact classification, Boost and correct tag anchors remain application content/rules. All alternatives must reconcile visible surfaces with collision geometry and preserve the controller goals in the prior reports.

Blender glTF can carry visual meshes/materials and some metadata, but does not standardize these gameplay semantics. A comparison should test conversion of the **same** ramp, collision proxy, rail centerline and wall annotation, rather than assume importing a GLB creates usable paths. The existing r137 loader and static batch impose additional known limitations [A1]. Blender's official MCP is a preferred candidate, not an approved installation; its generated Python can access/delete/transmit data, and source/version/permissions need explicit review [A1]. PlayCanvas also documents an Editor MCP [P5], but that is not approval to give any agent live write access or upload private assets. Offline reviewed scripts and native source backups remain alternatives.

### Web constraints, versions and hosting

- **Godot 4.5:** [G1] says WebAssembly and WebGL2 are required; its default single-thread web export does not need cross-origin isolation, while thread support and extension support do. Threaded export needs COOP/COEP and a secure context; the documented PWA service-worker workaround may simulate isolation when server headers cannot be set. This requires practical testing, especially first load, cache updates and third-party resources. GitHub Pages headers for this particular site were **not checked**; do not claim either guaranteed failure or guaranteed PWA success. The docs themselves have inconsistent prose about whether the generated HTML may be renamed; use the initial export names until verified. Godot 4.5 warns Safari/WebGL2 and mobile have caveats and limits web networking to HTTP, WebSocket client and WebRTC. C# web export is unavailable in this version, not a universal claim about every Godot release.
- **Unity 6.2:** [U1] specifically lists supported mobile browsers, correcting older blanket claims that Unity Web never supports mobile. [U2] says C# managed threads are unsupported on Web, native C/C++ threading is experimental and requires headers, and physics need not match native across platforms. [U3] describes Web-compatible Netcode; availability of a package does not choose hosting or authority. Its browser/C# JavaScript interop must be engineered for surrounding DOM and existing controls [U5].
- **Unreal:** Epic's accessible [E1] discusses HTML5 in general but does not identify which engine version supports that deployment. Its current URL returned legacy-sounding prose; it cannot establish official **UE5** local export. The separately maintained community [E2] explicitly documents a UE4 HTML5 extension, not official UE5 support. An Epic 5.8 release-notes fetch returned only a table-of-contents stub [E3]. We therefore **cannot verify UE5 local browser-export status**; do not infer it from UE4 or Pixel Streaming. Ask Epic's version-specific platform documentation/support before relying on it.
- **Graphics:** WebGL1 and WebGL2 are distinct hardware/browser capabilities; WebGPU availability is not universal. PlayCanvas currently documents WebGL2/WebGPU [P1], Godot 4.5 WebGL2 [G1], Unity 6.2 WebGL2 [U1]. Babylon's exact fallback and chosen version, the target device list and actual r137 compatibility need verification; no guarantee for WebGL1-only hardware is made. Different visual effects and texture compression can change support as much as engine selection.
- **Pages and downloads:** GitHub Pages is static hosting [H1]. It can serve a compatible client, not run a persistent room server. Its published-site maximum is 1 GB and soft bandwidth limit is 100 GB/month [H2]; suitability and current terms must be rechecked. Godot documents a WASM MIME type, compression and Pages gzip [G1]. Build payload, assets, initialization, requests, memory and ongoing bandwidth are **unknown here**, not equivalent to npm's unpacked package size. No exact sizes or 30 fps claims are measured.

## Proposed apples-to-apples evaluation — not authorized work

After explicit design and experiment authorization, compare the existing Three baseline and selected alternatives with the **same** representative Blender district slice, art/material targets, camera, fixed-step intent, input and movement behaviors: ramp takeoff/landing, body/underside clearance, deliberate curved Grind and Wall ride entry/exit, Boost, and a visible tag target. Make each engine expose what it actually supplies versus custom code. Preserve the original site/viewer, native art files and tests; avoid an engine-specific feature showcase masquerading as a workload match.

Measure cold/warm transfer bytes and startup, build outputs, CPU/GPU frame times and memory at comparable quality, actual 30 fps target adherence on agreed desktop/gamepad then representative phones, errors/retry and resource release. Test WebGL2 availability and browser compatibility rather than promising WebGL1. Measure authoring iteration, semantic fidelity, collision/path conversion, debugging and migration/reuse effort. Separately exercise 12–16 real/simulated visitors in **one** world with remote avatars and concurrent temporary tags, latency/loss/reconnect and abuse cases using the same explicitly chosen test backend; increase load to observe limits without a preselected player cap. A local render benchmark does not prove networking, and mock clients do not prove player experience. Record vendor costs, privacy and terms without uploading private materials to public services. None of these experiments ran.

## Decision briefing

**ENGINE-01 APPROVED direction:** retain Three.js with focused libraries. The alternatives remain reference material if that decision is reopened. The practical tradeoff is the total cost and quality of the **skating + original authoring + web embedding + one shared world**, not the label “engine.” Three minimizes transition friction but leaves integration work; Babylon and PlayCanvas may reduce some generic plumbing while introducing different scene/physics conventions; Godot/Unity may improve editor workflow while increasing rewrite and web-export constraints. Each can be reversed in principle, but reauthoring scenes, shaders, gameplay integration and tests makes reversal costly. Unreal's current local web route is insufficiently verified and streaming changes operational assumptions.

**Uncertainties:** desired local visual editing versus code, whether a public cloud project is acceptable, actual asset pipeline and AI trust boundary, supported devices/30 fps measurement criteria, downloadable bundle budget, server authority/hosting/security and acceptable ongoing cost. The previously chosen Three.js and experience goals remain intact until explicitly changed. Even approval of a different engine would not authorize an experiment, dependency installation, server or migration.

The comparison remains available for later questions; no migration or alternative-engine prototype is authorized.
