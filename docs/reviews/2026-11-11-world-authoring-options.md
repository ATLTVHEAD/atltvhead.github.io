# World-authoring options: Blender, CAD and code-assisted blockout

Research date: **2026-11-11**. Decision **WORLD-AUTHORING-01 — OPEN**.

**Outcome:** an original, artist-authored skating district is compatible with Three.js. Blender can supply editable art and placement authoring; CAD can supply dimensioned parts; scripts can assist either. **None of those tools automatically supplies the game's solid collision, grind rules, wall-ride semantics or linked skating flow.** The existing asset pipeline is not a general district importer. All recommendations below are **PROPOSED**, not architecture selection or implementation authorization.

Scope: read-only repository/source research, plus this one new report. This research task made no product/config changes or dependency installations and ran no Blender, servers, plugins/MCP setup, publishing, commits, deletion or worktrees. The parent session separately installed authorized locked test tooling; its evidence is attributed below. Existing untracked instructions, glossary and foundation audit were preserved. No repository code or assets were sent to external research services; searches concerned public tools/docs only.

## 1. Product constraints and authority

**APPROVED experience direction (user clarification relayed during research):** aggressive inline skating with fantasy high-tech rollerblades, momentum, jumps, tricks, grinds and wall rides; a **shared world first**, challenges later. The world is a compact, distinctive **District** with interconnected street-level, elevated and rooftop alternate routes. Natural ramp shape/speed takeoffs with deliberate Jump enhancement are chosen experience goals; the physics implementation remains **OPEN**. Desktop/gamepad first, touch phones second. Player-player collisions and crash ragdolls are later ambitions, not requirements for the first authoring evaluation. The current pack is unacceptable as final art; the user wants an editable, iterative, AI-assisted workflow for original world authoring in Blender or another CAD/DCC tool. Vocabulary: `GLOSSARY.md:1–33`.

**APPROVED retained style:** paper/cream + black ink + orange emphasis; stepped toon bands, selective outlines, restrained shadow-weighted halftone/hatching, original graphic signs/graffiti, compact streaks and a stable camera. This is explicitly retained from `docs/superpowers/specs/2026-10-28-skate-city-playability-and-comic-art-design.md:107–109`, not a request to revert to the current dusk-neon presentation. **SUPERSEDED final-art assumption:** the pack is the final primary visual vocabulary (`:101–103`); the comic direction survives. This does not authorize removing the source pack or editing that historical spec in this task.

Boost reserve is trick-fed and slowly drains while stopped. Long uninterrupted combos automatically trigger temporary unlimited-boost **Bomb Rush Mode**; the combo grace period is only a few seconds. **Inference:** an attractive city with widely separated skate spots can fail this game even if every model loads perfectly. Reachable opportunities, approach speeds, transitions, landing/runout and alternate links matter more than building count. The current movement tuning is not the final boost envelope, so no exact numerical gap distance or District dimensions are justified yet.

**Authority/history:** the earlier approved art spec accepted the Kenney pack and preserved established human scale (`docs/superpowers/specs/2026-10-28-skate-city-playability-and-comic-art-design.md:5–31`). The new final-art direction supersedes that pack choice, not human scale, the viewer or permission to delete assets. Natural takeoffs also reopen reliance on marker-only launches as the complete future experience; the relationship to approved marker/manual-Jump precedence needs explicit design reconciliation, not an automatic rule rewrite. The later planar document records a static authored irregular city, retained globe preview and inherited scale, although its status/implementation header is stale (`docs/superpowers/specs/2026-10-29-planar-wraparound-city-design.md:5–39,44–77,98–100`; foundation audit `:23–29`). No `docs/adr/` exists in this checkout. The approved launch-source exclusion, endpoint and manual-Jump rules remain separate history (`docs/reviews/2026-10-29-sol-skate-mechanics-review.md:150–163`).

**OPEN:** source-of-truth ownership, authoring tool/version, export contract, gameplay annotation/schema, coordinate conversion, district boundaries/topology, budgets and iteration workflow. A choice to compare Blender scenes is not approval of any of these. No physics engine, new dependency or Three.js upgrade is recommended here.

## 3. Four different things to author

This is a **PROPOSED conceptual separation**, not module boundaries or a schema selection. The same Blender project could contain all four; they need not be four runtime files.

| Concern | What it represents | What it cannot safely stand in for |
| --- | --- | --- |
| **Visual meshes/materials** | Building silhouettes, road dressing, rail tubes, decals, lighting-readable surfaces, decorative detail | A visual normal map is not physical roughness; a thin pipe mesh does not declare capture direction, exits or scoring. |
| **Solid collision proxies** | Deliberately simplified blocking/support geometry, openings and clearances suited to the eventual contact implementation | Overall art bounds are not accurate doorways; high-detail render triangles are not automatically an efficient or stable contact representation. Proxy type/consumer remains OPEN. |
| **Gameplay semantic paths/surfaces** | Grind centerlines/ledge edges, deliberately eligible wall-ride regions and orientations, launch/support relationships, spawn intent | Neither mesh edge extraction nor a material named “wallride” establishes the game's rules. Wall-ride behavior itself remains a separate design decision. |
| **Level layout source of truth** | Which modules exist, their transforms, district connectivity, vertical transfers, default arrival and line composition | A second independently hand-edited layout in JS/CAD/Blender risks drift, even if both exports individually validate. |

**Render triangles versus collision geometry:** glTF delivers rendering primitives. Decorative bevels, UV seams, material splits and smooth shading serve appearance; smoothing normals changes shading, not triangle positions. Collision needs dependable shape, clearance, sidedness and tolerances; semantic traversal needs intent. One mesh may be reusable for more than one purpose after validation, but equating all three makes contact behavior change when an artist adds trim or optimizes a facade. This is engineering inference from [S1–S5] and the repository contracts above, not a recommendation for a particular collider or engine.

## 4. Verified Blender → glTF → r137 facts

Sources [S1–S9] below identify versions and retrieval limitations. **Stable-reference scope:** Blender 5.1 manual text and official **4.5 release-branch exporter source**, not `latest`/development API promises. Source examined on that branch identifies exporter **4.5.47**. Neither is a choice of project tooling; an actual future export must be checked against the user's selected Blender/exporter version.

### Geometry, curves, coordinates and transforms

1. **Verified:** Blender exporter extracts triangulated mesh loops and splits vertices as needed for per-corner attributes; quads/n-gons become render triangles. UV/normal seams can increase exported vertex count. See [S1], [S4] `primitive_split` / `create_dots_data_structure`. **Inference:** do not use Blender's viewport face count as the delivered vertex/triangle budget, and review triangulation on non-planar ramp quads; a chosen diagonal can change the actual skating shape.
2. **Verified, version-specific nuance:** the manual says curves/non-mesh authoring data are not preserved as curves. The inspected **4.5 exporter actually attempts to convert `CURVE`, `SURFACE` and `FONT` objects to meshes** (`nodes.py`, `__gather_mesh` / `__gather_mesh_from_nonmesh`, [S3]). Therefore “all curves must always be manually converted” is too broad for this version. **But neither path preserves a Blender Bézier/NURBS rail spline as a native gameplay spline.** Unbeveled/loose edges additionally depend on export options; loose-edge export is off by default in inspected source [S2].
3. **Verified:** glTF core offers triangle/line/point primitives, not Blender spline control handles or CAD B-reps [S5]. r137 maps line modes to `LineSegments`, `Line`, `LineLoop`, not `THREE.Curve` or the game's skate paths (`lib/game/GLTFLoader.js:3090–3127`; [S6]). The planar mesh-only collector then skips lines. **Conclusion:** authored rail curves require an explicitly approved extraction/sampling handoff if they are to drive gameplay. A beveled curve can export the visible tube while separately losing the intended centerline semantics.
4. **Verified:** glTF uses a right-handed coordinate system, Y-up and meter distances [S5, §3.4]. Inspected exporter swizzles Blender `(x,y,z)` to `(x,z,-y)` when Y-up is enabled [S3, `__convert_swizzle_location`]; Y-up defaults true [S2]. r137 applies node matrix or TRS and builds hierarchy (`lib/game/GLTFLoader.js:3428–3540,3563–3580`). That does not repair the importer's raw-accessor bounds.
5. **PROPOSED caution:** verify one known dimension, origin, forward arrow and nested transformed instance end-to-end. Existing gameplay units are approximately 0.594 m/unit, not 1 m/unit (`asset-placements.js:3–10`). Do not double-convert axes, assume a scene-unit UI label applies every desired scale conversion, or apply the pack's 17× scale to original art. Applying transforms can simplify some contracts, but is not a universal remedy for hierarchy, mirrored normals, nonuniform scaling or metadata coordinates. A conversion policy remains OPEN.

### Materials and animation

- **Verified:** the manual/exporter supports recognized metal/rough PBR material arrangements and unlit materials via `KHR_materials_unlit` [S1–S4]. r137 supports core material loading and the unlit extension (`lib/game/GLTFLoader.js:258–277`). **Inference:** use a small representative material comparison in the actual game lighting; arbitrary Blender node graphs, procedural textures, compositor effects or a Blender “toon” look are not automatically transferred. Baking suitable appearances to textures is an option, not proof the result matches the intended art direction.
- **Retained comic style, implementation OPEN:** original silhouettes, cream/ink/orange palette, signs and some graphic texture treatment can be authored into assets. Stepped lighting, selective outlines and shadow-weighted halftone/hatching may instead need runtime presentation work or a deliberately authored/baked approximation; core GLB materials do not encode the complete required treatment. Compare a representative facade, skate surface and sign at chase-camera distance, including rail legibility and TVHead customization, before deciding that split. Restrained marks and bounded streaks must not become mandatory camera shake or a full-screen obscuring filter (`2026-10-28-skate-city-playability-and-comic-art-design.md:107–111`). No shader/postprocessing architecture is selected.
- **Verified:** glTF animation supports node translation/rotation/scale and morph weights; skins are a separate asset representation [S5, §§3.7.3,3.11]. Blender's export modes/sampling and shape-key/skin controls are explicit [S2]. r137 builds tracks for those core properties (`lib/game/GLTFLoader.js:3250–3336`). These are not Blender constraint graphs, gameplay interactions, collisions or ragdoll rules. Newer `KHR_animation_pointer` export options in [S2] must not be assumed supported by this loader. Static world art does not require the first comparison to include character animation.

### Custom properties, extras and extensions

- **Verified:** enabling **Custom Properties** exports eligible properties as glTF `extras`; inspected source defaults `export_extras` to **false** [S1–S3]. JSON-compatible values are filtered/converted; some internal properties are excluded [S3, `extras.py`]. Do not assume every Blender-specific property survives.
- **Verified:** glTF `extras` is application-specific data with no standard gameplay meaning [S5, §5.16]. Extensions are a distinct mechanism with `extensionsUsed` / `extensionsRequired` declarations [S5, §3.12]. Neither mechanism makes a standard GLB automatically grindable or wall-rideable. No metadata vocabulary, version field, namespace or extension is chosen here.
- **Verified r137 behavior:** object-valued extras are shallow-assigned into `userData`; primitive-valued extras are warned about/ignored (`lib/game/GLTFLoader.js:1794–1808`). Node extras are assigned after original name metadata (`:3506–3514`); meshes, materials, scene groups and primitive geometry have their own attachment points (`:2954,3141–3143,3571–3574,3856`). **Inference:** metadata location and allowed keys matter; arbitrary extras can collide with other `userData` keys. There is no automatic coordinate transformation of numeric point arrays inside extras.
- **Verified:** r137 sanitizes/deduplicates names (`lib/game/GLTFLoader.js:2967–2979`) and can turn a multi-primitive mesh into a group (`:3158–3175`). **Inference:** don't treat current object name or child index as a stable gameplay ID without a chosen contract. Capture helper data before static batching if such a handoff is approved; inspecting only final batched meshes loses the source hierarchy/intent.

### Compatibility traps with an older renderer

**Verified:** r137's built-in handler list is finite (`lib/game/GLTFLoader.js:8–61,251–295`; [S6]). It has no built-in `EXT_mesh_gpu_instancing` or `KHR_animation_pointer` handler. A current exporter having an option is not evidence this runtime understands it. Unknown required extensions only emit a warning in the inspected generic branch (`:280–285`); apparent loading success is not compatibility validation.

Draco, KTX2/Basis and meshopt pathways require corresponding loader/decoder setup for compressed content; the game only constructs `new THREE.GLTFLoader()` (`game-assets.js:41`; loader `:8–10`). **PROPOSED comparison baseline:** ordinary uncompressed geometry plus core PBR/PNG/JPEG or a specifically checked unlit material, without GPU-instancing/novel animation extensions. This is a reversible compatibility-control suggestion, not a permanent optimization ban, dependency installation or renderer-upgrade decision. Compression, material extensions and batching require separate evidence/approval if later wanted.

**Verified validator scope:** Khronos glTF-Validator checks JSON/GLB structure, references, buffers/accessor values/bounds, supported extensions and reports asset stats [S7]. Its browser tool is documented as client-side. **Inference:** validator success does not certify r137 feature support, our import bounds, collision alignment, gameplay IDs, flow, performance or asset rights. No asset was uploaded or validated in this session.

## 5. CAD: practical bridge versus direct export

**Verified:** FreeCAD documentation describes converting parametric shapes to **non-parametric meshes**, with surface/angle deviation and mesh-size controls [S8]. FreeCAD **1.0.2** source routes `.glb`/`.gltf` export to its glTF writer. That writer uses OCCT, requires OCCT ≥7.5, sets input length unit **0.001** and Z-up, and chooses binary output from the `.glb` extension [S9]. This is version-pinned source evidence, not proof of the user's installation/build or any successful export here.

**Practical routes, neither selected:**

- **CAD → tessellated GLB or OBJ → Blender → game export:** keep dimensioned/parametric parts in their native CAD source; use Blender for mesh inspection/cleanup, material/UV work, arranging pieces and gameplay annotations if that authoring boundary is approved. GLB can carry scene/material structure; OBJ is a mesh bridge rather than a retained parametric model. Keep the CAD source: a mesh roundtrip does not preserve editable constraints/solid construction history. Do not assume stock Blender imports STEP directly; no STEP add-on was investigated or approved.
- **CAD → GLB → game:** FreeCAD can export glTF directly in the pinned implementation [S9], so Blender is not logically mandatory. But direct export still needs scrutiny of triangle density, normals/materials, hierarchy/pivots, dimensions and separately supplied gameplay data. It does not bypass this repository's pack importer or bounds problem. If material/mesh cleanup is consistently necessary, the Blender bridge earns its cost; if a representative part already meets the contract, an extra conversion may add little value.

**Inference:** CAD is strongest when the user prefers constrained dimensions, repeated engineered structures and parametric ramps/rail assemblies. Mechanical precision is not automatically skating quality. Very fine tessellation can retain tiny fillets/fasteners irrelevant at chase-camera distance; coarse tessellation can turn a smooth transition into visible/contact facets. Render tessellation and any collision/path sampling should be evaluated separately. No tessellation tolerance, mesher or CAD dependency is selected.

## 7. AI assistance: verified capability, not promised art quality

**Verified:** Blender has a Python API and supports script execution through its UI/command line. The 4.5 LTS command-line documentation lists background mode, explicit Python scripts and `--python-exit-code` [S10]. The official exporter exposes controllable export options [S2]. **Inference:** an AI assistant can draft reviewable scripts for modular geometry, object placement, measurements, naming checks, curve sampling or repeatable export. This is a method using ordinary scripting—not a guarantee a particular AI product understands topology, styling, Blender context or skating design.

**Current first-party support does exist, with important limits:** Blender's official Lab MCP page describes a natural-language interface to the Python API, requires **Blender 5.1+**, a separately installed add-on, client and MCP server, and says Blender does not have built-in LLM connectivity [S11]. Its project releases list **v1.0.3, 2026-09-11** [S12]. This supports describing it as an actively maintained first-party **Lab integration**, not a standard built-in feature or a required pipeline tool. No setup or use is authorized here. The selected Blender version may differ; 4.5 source compatibility research does not establish compatibility with that MCP integration.

**Verified security warning:** the official Lab page explicitly warns generated code runs without guards against deleting data or sending it remotely and recommends isolation from sensitive information [S11]. Blender's scripting-security manual says Python is unrestricted; manually running a script is distinct from disabling automatic script execution [S13].

**PROPOSED control comparison:**

| Assistance mode | Useful control | What remains risky/unproven |
| --- | --- | --- |
| **AI drafts scripts, human reviews before execution** | Inspect text, parameters, file outputs and changes; work on a separate saved scene; compare results before accepting. Good candidate for repeatable modular tasks. | A reviewed script still executes arbitrary Python. Headless mode is not a sandbox; mistakes can overwrite files or regenerate away manual work. A prompt alone is not a reproducible build. |
| **Live agent/plugin/MCP interaction** | Scene inspection and short interactive requests may make iteration faster; official integration is a verifiable example. | Additional installed trust/network/execution boundary; review can lag behind actual mutations. Neither “official” nor local sockets provide a Python sandbox. Human permission, isolated execution and backup policy would need separate approval. |
| **Generated mesh import from an AI service/tool** | Could provide reference shapes or decorative starting points if the user chooses one. | No service evaluated here. No assurance of editable topology, exact scale, usable UVs, contact-ready surfaces, consistent style, provenance or commercial rights. Cleanup/re-authoring may exceed creation time. Never make such geometry the unreviewed source of gameplay truth. |

For reproducibility, preserve native source, reviewed script/inputs, actual tool/exporter versions and export settings; compare semantic/dimension invariants as well as file hashes. A hash proves byte identity, not editable intent, and repeated exports are not assumed byte-identical. Use snapshots/Save As and a scoped generated collection/output rather than relying solely on Undo: filesystem/network effects are outside ordinary scene undo, and a generic script may not form one clean undo step. These are **PROPOSED safeguards**, not authorization to create files or run scripts now.

## 8. Conceptual asset handoff alternatives

The user owns these boundaries. They are independent of whether A, B or C is explored; none defines an approved schema.

1. **One exported scene, including intentional helper nodes/extras:** a chosen extraction stage reads visual nodes, authored proxies and gameplay helpers before static batching. Spatial co-authoring reduces duplicate coordinates. Risks: helper filtering, property conversion, hierarchy/name changes, optimization stripping, local/world transforms and collision with `userData` keys. The current renderer does not do this.
2. **Visual GLB plus a gameplay/layout sidecar exported from the same authoring source:** easier textual review and independent validation of paths/proxies; stable source IDs could associate records. Risks: stale pairs, coordinate mismatch and schema ownership. An atomic/version-associated export is a conceptual safeguard, not a selected manifest/schema or build system.
3. **Module GLBs plus a code/data-authored level:** placement and semantic layout remain explicit and testable outside Blender, potentially closest to the existing seam. Risks: losing visual layout convenience and independently adjusting Blender art beyond the gameplay envelope. A district GLB and repeated module library can coexist, but chunking/streaming/instancing policies are not decided by that observation.

For each handoff, **OPEN source-of-truth question:** is district placement authoritative in `.blend`, in CAD parameters, or in a text layout? Which outputs are generated/read-only, and what can the artist change without a code edit? Avoid two independently editable authorities for the same transform. Different concerns can have different owners, but their relationship needs explicit approval.
